# AI 提效个人易，组织变革难：软件工程的 5+2 新范式

> 个人用上 AI 之后，组织交付未必变快。本文把这一现象放回软件协作链路与价值流，提出面向 AI 时代的组织与工程范式——**5+2**：五个主体变化（角色、组织、工艺、流程、资产），加上两个支撑系统（工具、治理）。
>
> 文中关键判断尽量对照可核验研究与成熟框架（DORA、Team Topologies、Architecture as Code、NIST AI RMF 等）；**5+2 本身是实践提案**，用于把既有理论组织成可落地的操作系统，而非取代任一行业标准。全文按证据与理论锚点、范式总览、分章展开、反模式与试点路径推进，文末附参考文献。

AI 降低「写出代码」的边际成本，但若协作方式、验证机制与治理边界不变，个人吞吐会被评审、测试、环境与跨团队协调吸收。AI 首先是**放大器**，放大的是组织既有能力与既有缺陷。

先给一个直接答案：

> **真正的问题不是「个人能不能变快」——答案已经足够清楚；而是：个人变快之后，组织有没有新的协作方式、验证机制与治理边界来承接这种变化？**

## 摘要

个人用上 AI 之后，组织交付未必变快：AI 降低「写出代码」的边际成本，却会放大既有的评审、联调、环境与治理瓶颈。本文提出面向 AI 时代的实践提案 **5+2**：角色、组织、工艺、流程、资产五个主体变化，加上工具与治理两个支撑系统。判断对照 DORA、Team Topologies、Architecture as Code、NIST AI RMF 等可核验框架；5+2 用于把既有理论组织成可试点的操作系统，而不是取代任一行业标准。文末给出反模式与「先让一个产品跑起来」的路径。

## 1. 开篇：个人提效与组织提效的错位

过去一年，很多研发组织里都能看到相似现象：AI 从个人尝鲜，进入日常研发。

产品经理用 AI 生成原型，工程师用它阅读与生成代码、补充测试，测试人员用它整理用例与分析缺陷，架构师也开始借助它做方案评审与影响分析。从个人视角看，变化是实在的：陌生代码可以先梳理主线，样板代码可以先出初稿，易遗漏的测试点可以先补一轮。

但回到组织层面，管理者的感受往往没那么强。需求仍在排队，版本仍按原节奏推进，跨团队沟通、测试环境、联调与评审仍需反复协调。每个人似乎都快了一点，组织整体却未必同步变快。

### 1.1 证据三角：局部加速、链路阻塞、组织放大

可以把现有证据粗分为三类，它们并不互相否定，而是描述同一现象的不同切面。

| 证据层 | 代表研究 | 主要发现 | 启示 |
| ------ | ------ | ------ | ------ |
| **任务层加速** | Peng 等，GitHub Copilot 受控实验 | 独立 JS HTTP Server 任务上，Copilot 组约快 **55.8%**[^peng-2023] | 边界清晰、上下文有限时，个人编码吞吐可显著提升 |
| **成熟仓上的摩擦** | METR 2025 RCT | 资深维护者在自有大仓任务上用 AI 约慢 **19%**，却仍主观感知更快[^metr-2025] | 高耦合、高上下文任务上，收益会收缩甚至反转；**感知 ≠ 实测** |
| **组织层悖论** | Faros 2025 遥测 | 高 AI 采用：任务约 **+21%**、PR 约 **+98%**，PR 评审时间约 **+91%**；公司层交付绩效几乎无显著相关[^faros-2025] | 个人/小队吞吐上升，会被评审与下游链路吸收 |
| **放大器效应** | DORA 2025 | AI 近乎普及（约 **90%** 受访者使用）；AI 与吞吐、产品绩效正相关，但与**交付稳定性负相关**；高质量内部平台显著放大 AI 收益[^dora-2025] | AI 不修复组织，而是**放大**既有能力与缺陷 |

合在一起，图景更清楚：

> **个人（或局部任务）的加速可以发生；组织级交付变快且稳定，不会自动发生。**

软件交付从来不是一个人的工作，而是一条协作链路：需求澄清、方案评审、代码合入、测试验证、环境与数据准备、发布协同、问题追踪。若这些环节仍按旧方式运转，只是每人多了一个 AI 工具，组织效率就很难出现根本变化——这正是 Amdahl 定律在工程链路上的体现：系统速度受最慢环节约束。[^faros-2025]

因此，AI 给软件工程带来的第一个问题，不是「个人能不能变快」——答案已经足够清楚。

> **真正的问题是：个人变快之后，组织有没有新的协作方式、验证机制与治理边界来承接这种变化？**

## 2. Why：成本结构、理论锚点与新约束

### 2.1 成本结构正在重排

AI 改变的不只是开发工具，而是软件开发的**成本结构**。

过去，很多研发组织最大的瓶颈是开发产能：需求来了要排期，方案定了要等人写代码，功能一复杂就要堆更多开发资源。现在，代码理解、生成、测试补充、缺陷分析与文档整理的成本正在下降。「写出代码」仍重要，但正从最稀缺的能力，变成可被 AI 大幅放大的能力。

| 相对旧瓶颈 | 相对新瓶颈 | 组织含义 |
| ------ | ------ | ------ |
| 编码产能 | 需求澄清与边界定义 | 产品与工程更早共创；Spec / 契约质量决定下游吞吐 |
| 样板实现 | 架构边界与契约兼容 | 适健函数与自动化评审优先于口头规范 |
| 手工补测 | 自动化验证与环境/数据就绪 | Test Builder / 平台能力成为吞吐上限 |
| 个人知识 | 可被 Agent 消费的上下文 | 资产与本体成为生产力要素 |
| 功能上线 | 安全合入、价值验证与成本可控 | 治理与 FinOps 进入交付主路径 |

与此同时，AI 又带来大量新应用需求：智能客服、智能运营、智能分析、个人/企业智能体、知识库问答、流程自动化与人智协同平台。软件系统不只给人使用，也要给智能体调用；不只提供页面，还要提供接口、上下文、权限、工具与可审计的执行环境。

### 2.2 四个理论锚点

5+2 不是凭空发明，而是把几条成熟约束重新组合到 AI 语境：

| 锚点 | 要点 | 对 AI 时代的含义 |
| ------ | ------ | ------ |
| **Amdahl 定律** | 系统加速受未优化部分限制 | 只加速编码，评审/测试/发布不动，整体收益很快饱和[^faros-2025] |
| **Conway 定律** | 系统结构映射沟通结构 | 人智协作要有对应的组织接口；否则 Agent 只会加剧跨墙摩擦[^conway] |
| **认知负载（Team Topologies）** | 团队认知预算有限 | AI 可卸下部分内在负载，但会把新负载推到编排、验证与治理；需平台与启用团队承接[^team-topologies] |
| **价值流 / 约束理论** | 优化非约束环节无效甚至有害 | 应先定位价值流真实约束（常是澄清、评审、环境），再决定把 AI 用在何处[^dora-2025] |

DORA 2025 把这一点说得很直白：AI 是放大器；高绩效组织用它变得更强，脆弱组织则更容易暴露耦合架构、慢反馈与薄弱测试。[^dora-2025]

### 2.3 软件工程范式的迁移

可把当前实践理解为三种并存范式（而非严格替代）：[^arxiv-hai-se]

| 范式 | 人类主贡献 | AI 角色 | 组织关键能力 |
| ------ | ------ | ------ | ------ |
| **Traditional** | 亲手编写与审查 | 无或弱辅助 | 经典 SDLC 与职能协作 |
| **Generative AI-enabled** | 意图、审查、集成 | 生成草稿与局部加速 | Prompt 素养、评审吞吐、测试门禁 |
| **Agentic AI-enabled** | 意图设定、编排、验证、问责 | 多步执行与工具调用 | Harness、评测、权限、审计、风险分级 |

多数组织正处于第二段，并局部进入第三段。5+2 的目标，是让组织在进入 Agentic 阶段时，有角色、组织、工艺、资产与治理可承接，而不是只靠个人技巧。

> AI 时代的软件工程变革，不能停留在个人效率；必须进入一套新的**组织与生产关系**。这就是下文的 **5+2**。

## 3. What：5+2 新范式——用新的生产关系承接新的生产力

为什么需要一套新范式？因为 AI 同时改变了两件事：

1. **成本结构变了**：过去依赖人力堆出来的大量工作，现在可由人与 AI 一起完成。
2. **系统需求变了**：软件不只给人用，也要给智能体调用。

研发工作内容随之扩展。团队要额外回答例如：

1. 需求能否被 AI 快速、准确地理解？
2. 代码库能否被 AI 安全修改？
3. 测试能否被 AI 自动执行并给出可信反馈？
4. 环境与数据能否被快速准备？
5. 知识能否被持续复用（而不只存在于某人脑海）？
6. 架构原则能否被自动守护？
7. 高风险决策何时必须由人审核？
8. AI 带来的成本与收益能否被度量？

这些问题超出单个工具的范围：会催生新角色，要求新流程与工艺，沉淀新工程资产，需要新工具平台承载，并要求新的治理模式。

### 3.1 5+2 总览

| 维度 | 名称 | 一句话 |
| ------ | ------ | ------ |
| **1/5** | 新角色 | 从 Developer 到 Builder；Expert 转向能力沉淀与复杂性治理 |
| **2/5** | 新组织 | FDE / 产品 / 平台三层协同，而非单纯职能墙 |
| **3/5** | 新工艺 | 创意、需求、交付、运营四大闭环 + 知识与经验两个底座 |
| **4/5** | 新流程 | 代码与能力在三层之间「内部开源」式流动 |
| **5/5** | 新资产 | 工程资产 + 语义连接 + 可复用的 Skill / 记忆 / 评测 |
| **1/2** | 新工具 | Delivery Workbench + Agent Harness（编排、验证、护栏、观测） |
| **2/2** | 新治理 | 先建可验证安全网，再按风险放大 Agent 自主度 |

### 3.2 与外部框架的映射（便于落地沟通）

5+2 可视为「操作系统」；下列框架是已获广泛认可的「组件标准」。映射不是一一等价，而是减少沟通成本。

| 5+2 维度 | 可对齐的外部概念 | 说明 |
| ------ | ------ | ------ |
| 新角色 / 新组织 | **Team Topologies** 四类团队 | FDE≈价值流对齐团队；产品含复杂子系统与专家能力；平台≈Platform；Expert/启用≈Enabling[^team-topologies] |
| 新组织 / 新工具 | **Platform Engineering**（DORA） | 高质量内部平台与 AI 价值释放显著相关[^dora-2025] |
| 新工艺 / 新流程 | **价值流管理（VSM）** | 把 AI 打在真实约束上，而非加速已很快的环节[^dora-2025] |
| 新工具 | **Harness Engineering** | 把模型能力变成可生产使用的编排、验证、记忆、护栏与观测[^harness] |
| 新治理 | **Architecture as Code / Fitness Functions** | 架构意图可版本化、可测试、可进 CI[^arch-as-code][^evo-arch] |
| 新治理 | **NIST AI RMF**（Govern–Map–Measure–Manage） | 政策、角色、风险测绘、度量与处置的治理骨架[^nist-ai-rmf] |
| 新治理 / 度量 | **DORA 指标 + AI 专用指标** | 吞吐与稳定性并重；补 Token、评测、评审负荷等 |

5+2 不是七个概念的罗列。它要回答的是：

> **如何把个人使用 AI 的效率，转化为小队、产品线与组织的系统效率——并且在加速的同时守住稳定性与责任边界。**

## 4. 新角色：从 Developer 到 Builder

5+2 的第一件事，是角色。

AI 时代的研发组织，不再只围着 Developer 切分工，而会逐步围着 **Builder** 运转。Builder 不是换个岗位名：人不再只守住某一个狭窄环节，而是与 AI、Agent、平台和资产一起，把业务问题构建成可运行、可验证、可持续演进的系统。至少会出现五类 Builder。

### 4.1 五类 Builder

#### Product Builder：从需求管理者到产品构建者

来自产品经理，但不止于写需求、排优先级、开评审。在 AI 辅助下，可以更快出原型、与业务共创、用数据判断效果；具备编码能力时，还能在 Agent 或前端 FDE 协助下改简单页面，快速验证想法。DORA 强调 **user-centricity** 是 AI 成功的前置条件：AI 要对准清晰用户问题，而非漫无加速。[^dora-2025]

#### Application Builder：从写代码的人到应用系统构建者

Developer 演进的主线。代码理解、生成与测试成本下降后，开发会更全栈——不只前后端一体，还会走向应用、数据、算法一体。他要更靠近业务：参与澄清、原型、方案与价值反馈；同时带着 Agent 守质量，覆盖自动化测试、影响分析、回归、文档与基础质量闭环。工作重心从「打字」转向「定义任务、审查输出、做判断」。[^arxiv-hai-se]

#### Agent Builder：从使用 AI 到构建 AI 能力

不是写 Prompt 的人，而是建设智能体能力的人：设计工作流、沉淀 Skill、连接工具、组织上下文、做评测，并管理记忆、权限与版本，让 Agent 能稳定参与交付。

在此体系里，**Agent 是执行主体，Skill 是可复用能力**。成熟组织不会长期依赖临时 Prompt，而会把高频任务沉淀为 Skill，再经版本化、评测与治理持续演进。Agent Builder 与知识工程高度重叠——好的 Agent 离不开知识资产、本体网络、业务规则与上下文组织。

#### Test Builder：从测试执行者到质量基础设施构建者

测试不会消失，重心会变。当开发在 Agent 辅助下能完成更多自测、自动化与功能验收，手工执行型测试占比下降；Test Builder 更多转向测试基建、专项测试、覆盖强化、质量门禁、测试数据、**Agent Eval** 与自动化策略——不只发现问题，而是构建质量体系。DORA 与 Faros 都指出：加速后若验证跟不上，稳定性与缺陷会承压。[^dora-2025][^faros-2025]

#### Platform Builder：从平台支撑者到组织能力构建者

来自平台、架构与支撑团队。一线小队要跑得快，背后要有 AI、数据、知识、工程平台，以及 CI/CD、环境、权限、观测、FinOps、架构守护、公共工具链、公共 Skill 与 **Agent Harness**。工作不是被动响应项目，而是沉淀组织级能力（平台即产品），让更多 FDE 小队低成本复用。[^dora-2025][^harness]

### 4.2 责任分工一览

| 角色 | 主责（Own） | 常与 Agent 协作的方式 | 典型产出 |
| ------ | ------ | ------ | ------ |
| **Product Builder** | 问题定义、优先级、价值假设 | 原型生成、竞品/场景展开、指标解读 | 场景、BRD、原型、验收意图 |
| **Application Builder** | 可发布变更与质量闭环 | 实现、重构、影响分析、文档同步 | Spec、代码、测试、发布包 |
| **Agent Builder** | Agent/Skill 可靠运行 | 工作流设计、工具接入、评测迭代 | Skill、评测集、权限策略、运行手册 |
| **Test Builder** | 质量信号可信 | 用例生成、缺口分析、门禁策略 | 测试基建、覆盖策略、质量门禁 |
| **Platform Builder** | 组织级复用与安全边界 | 平台 API、Harness、观测与成本 | 平台服务、CLI、护栏、FinOps 视图 |
| **Expert** | 标准与复杂性治理 | 规则编码、疑难诊断、例外审批 | 适健函数、ADR、能力包、培训 |

### 4.3 小队怎么配，Expert 怎么放

一线小队不再是传统「产品 + 开发 + 测试」的简单拼装：Product Builder 管判断与原型，Application Builder 管交付与质量闭环，Agent Builder 管智能体与 Skill；Test Builder、Platform Builder 多在产品/平台侧支撑，也可按阶段前置到一线。

Builder 化不等于 Expert 消失。一线变宽之后，反而更需要少量高水平 Expert 管理复杂性——Architecture、Performance、Security、UX、Frontend、Backend、Testing、Data 等仍然关键，但方式要变：从流程末端的审批关口，转为产品/平台团队里的能力中心，负责标准、资产、工具链与质量门禁。这接近 Team Topologies 中 **Enabling team** 与 **Complicated-subsystem team** 的组合：短期赋能、长期把复杂子系统与标准沉淀为可消费能力。[^team-topologies]

> **Builder 负责交付闭环，Expert 负责能力沉淀与复杂性治理；Agent 负责可验证的执行带宽。**

角色变化的本质，不是人人变成超级个体，而是组织围绕 Builder、Agent、资产与平台重新分工。

## 5. 新组织：FDE、产品、平台三层协同

角色变了，组织也必须变。若仍按职能墙切分，五类 Builder 很难真正发力——个人快了，协作链依旧很长，组织依旧慢。

可演进为三层结构。其中 **FDE**（Forward Deployed Engineer / 前置交付工程）概念源自 Palantir：工程师嵌入业务现场，面向具体客户与场景快速交付，并把一线经验回馈平台与产品；「Dev」做一能力服务多客户，「Delta/FDE」做一客户解决多能力。[^palantir-fde] Anthropic、OpenAI 等 AI 公司也在采用类似前置交付模式。本文借用其精神——**前置业务、快速闭环、经验回灌**——而不是照搬某一家的编制。

### 5.1 与 Team Topologies 的对应

| 本文层级 | Team Topologies 近似 | 互动模式倾向 |
| ------ | ------ | ------ |
| **FDE 小队** | Stream-aligned（价值流对齐） | 端到端交付；对平台多为 X-as-a-Service |
| **产品团队** | Stream-aligned + Complicated-subsystem / Enabling | 产品化、熵减；专家以内嵌或短期赋能方式介入 |
| **平台团队** | Platform | 以内部产品降低认知负载；提供 Harness 与工程自服务 |

目标一致：**降低一线认知负载，加快价值流动，避免把专家变成永久审批墙**。[^team-topologies]

### 5.2 第一层：FDE 团队——前置业务，快速闭环

由多个业务小队组成，每队约 3–5 人。不是传统项目组，而是前置到具体场景，围着澄清、原型、契约驱动开发、验收与价值反馈转闭环。

小队通常含 Product、Application、Agent Builder；Test / Platform Builder 可按阶段临时加入。多个小队可合成领域团队，面向一个业务域沉淀经验、资产、Skill 与最佳实践。

**价值**：让业务变化更快变成可运行、可验证的软件变化。

### 5.3 第二层：产品团队——长期健康与熵减

复杂产品可拆成多个 3–5 人产品小队，再组成产品线，负责产品或产品族的长期演进。职责不止需求管理与排期，还包括产品架构、共性需求、复审、重构、技术债、测试强化与发布。

FDE 可以快速改产品，但不能长期停在局部最优。产品团队负责复审、吸收、重构与熵减，把一线创新沉淀为产品能力。Architecture、UX、Frontend、Backend、Testing、Performance、Security 等 Expert 可作为成员嵌入：不是专职审批人，而是持续建设标准、工具、Skill 与质量门禁。

**价值**：守住产品长期健康。

### 5.4 第三层：平台团队——组织级底座复用

底层含 AI、数据、知识、应用、工程等平台，为 FDE 与产品提供可复用能力：模型接入、Agent 运行与评测、权限与观测、Token 成本；数据资产与口径；本体与记忆；环境、CI/CD、CLI、自动化测试与发布治理；以及面向 Agent 的 **Harness（编排 / 验证 / 护栏 / 观测）**。

平台也应由多个小队组成，而非一个大而全的中心；每个小队围着一类能力演进，以工具、接口、Skill、规则与服务对外提供。DORA 数据显示：约 **90%** 组织已有平台实践，且高质量内部平台与释放 AI 价值直接相关。[^dora-2025]

**价值**：组织不必在每个产品、每个小队里重复造底座；模型可租用，**Harness 与平台能力应自有并复利**。[^harness]

### 5.5 三层如何协同

三层不是上下级审批，而是基于资产与智能体的能力流动：

```text
FDE 快速探索 → 产品复审重构沉淀 → 平台底座化
平台能力回推产品 → 产品能力回推 FDE（交付成本持续下降）
```

组织不再只靠职能分工运转，而是通过三层协同，把一线变化持续沉淀为产品能力与平台能力。

## 6. 新工艺：四大闭环 + 两个底座

有了角色与组织，还要有工艺。

过去交付常被理解为线性链路：需求 → 设计 → 编码 → 测试 → 发布。AI 时代它仍有价值，但不够——工作可以更早发生、更快验证、更频繁反馈。新工艺不是把线性流程切得更细，而是把关键工作做成持续闭环：**四大闭环，加两个底座**。

工业现场研究也支持这一方向：当 AI 从「局部工具」升级为嵌入分解、验收标准校验、仓库原生评审与人机混合执行的交付编排时，速度与下游质量更容易同时改善。[^chiron-2026]

### 6.1 创意闭环：业务 → 产品/Agent → 原型 → 业务

解决「做什么、值不值得做」。业务提出问题，Product Builder 借助 Agent 快速生成原型、场景与价值假设，再回业务讨论、试用、调整。产出不是完整 PRD，而是场景、假设、原型与 BRD——低成本把想法变成可讨论、可试用、可调整的东西。

### 6.2 需求闭环：产品 → 编码 Agent → 问题 → 产品

解决「需求能不能落进现有系统」。产品不再闭门写 PRD，而是让编码 Agent 读代码、接口、数据、历史需求与约束，反向提问；产品据此澄清边界、异常、权限、状态流、兼容性与验收标准。产出是高质量 PRD、澄清清单、验收标准与需求契约——需求在进开发前就与真实系统碰撞。

**Spec / 契约驱动**是此环的关键工艺：把意图写成 Agent 与测试都能消费的结构化规格（接口契约、验收用例、不变量、禁止事项），减少「看起来合理但无法验证」的自然语言歧义。[^thoughtworks-agentic]

### 6.3 交付闭环：Builder → Spec → Coding → 测试验收 → Builder

解决「如何交付可验证的系统变化」。Builder 与 Agent 把需求转成 Spec，再设计、实现，并在真实或准真实环境完成验收。质量不落在最后一道关，而内嵌全过程：自动化测试、CLI 环境、造数、AI 代码评审、架构规则、功能与回归。产出是 Spec、设计、代码、测试、验收结果与可发布版本。

推荐把交付闭环显式拆成可中断的子循环：

```text
Plan → Implement → Verify → Review → Ship → Reflect
        ↑_______________|（失败则回退并强化 Harness / 测试）
```

「Anytime the agent makes a mistake, engineer the harness so it never makes that mistake again」——这是 Harness Engineering 的核心纪律，也应成为交付工艺的一部分。[^harness]

### 6.4 运营闭环：FDE → 运营数据 → 调整系统 → FDE

解决「上线后有没有创造价值」。FDE 持续观察行为、指标、日志、反馈与实验，推动下一轮调整。产出是运营数据、价值评估、优化清单与下一轮需求——交付代码不是终点，交付价值才是。

### 6.5 底座一：知识联通

关键知识尽量落在代码库或强关联资产中：需求、设计、代码、测试、数据脚本、契约、规则、运营数据、决策记录不应孤立。经本体网络、语义/向量检索与代码引用连接起来，人和 Agent 才能低成本拿到上下文。

### 6.6 底座二：经验进化

每次交付、失败、评审、测试与运营反馈，都应沉淀为可复用经验：Prompt、Skill、Agent 记忆、失败案例、测试集、质量与架构规则、专家经验——版本化、评测、持续改进，反哺 Agent、规则与流程，让组织越用越强。

> **四个闭环让业务想法持续变成价值；两个底座让知识与经验持续进化。**

## 7. 新流程：代码与能力在三层流动

新工艺回答「一次需求如何闭环」；新流程回答「组织内部如何流动」——允许前线更快探索，也允许后线持续熵减。

| 层级 | 怎么流动 |
| ------ | ------ |
| **FDE** | 围着四大闭环快跑；可改产品代码，必要时改平台代码。产品/平台智能体参与设计与架构评审，用于早发现问题与风险，**不成为低风险探索的阻塞点** |
| **产品** | 接收 FDE 贡献与场景经验 → 复审、重构、熵减、测试强化、产品化发布；必要时推动平台补齐。前线代码不必一开始最优，验证了业务价值就应被吸收 |
| **平台** | 接收共性改动 → 复审、优化、测试、平台化发布，再回推产品与 FDE |

> **前提**：自动化测试与架构适健函数足够强——否则产品/平台不敢重构前线代码，FDE 也不敢探索。这与 DORA「加速暴露下游弱点」的判断一致。[^dora-2025]

新流程的本质不是多一层审批，而是**内部开源式流动**：FDE 探索，产品沉淀，平台底座化；智能体参与评审但不替代责任。流程关键从「谁先批准」变为「谁快速贡献、谁持续熵减、谁稳定复用」。

贡献合入建议遵守最小质量契约：

1. **可验证**：自动化测试 / 契约测试通过；
2. **可回滚**：变更可逆，爆炸半径可控；
3. **可追溯**：意图、引用上下文、Agent 轨迹可审计；
4. **可沉淀**：值得复用的 Skill / 规则 / 文档同步回流。

## 8. 新资产：从文件堆叠到语义连接

DevOps 强调 Everything as Code。AI 时代仅「代码化」不够——模型与 Agent 需要完整上下文；**Context Engineering**（为 Agent 组织正确、充分、及时的上下文）正成为与 Prompt Engineering 同等重要的工程能力。

资产边界扩大：需求、设计、代码、测试、数据脚本、契约、日志、评测集、架构决策、历史缺陷；以及过去常被忽视的 **Agent 执行过程数据**——如何拆任务、调了哪些工具、参考了哪些文档、何处失败、人类如何纠偏、Skill 在何种场景稳定或失效。过程数据不能只是临时日志，应被保存、结构化、评测与复盘，用于优化 Prompt、沉淀 Skill、增强记忆与扩充评测集。

资产多了却只堆进仓库，价值仍有限。关键是用本体网络把概念、系统、实体、契约、规则、测试、指标、缺陷与决策连起来，检索才能沿业务语义与工程依赖走，而不只靠关键词或向量「猜」。

| 层级 | 内容 | 工程要求 |
| ------ | ------ | ------ |
| **底层工程资产** | 需求、设计、代码、测试、数据脚本、契约/API、运行日志、评测集、Agent 执行轨迹 | 版本化、可引用、与变更同生命周期 |
| **语义连接层** | 本体网络 / 知识图谱：概念、系统、数据、规则、接口、测试、经验 | 显式关系 > 纯相似度；可演进、可校验 |
| **能力资产** | Agent 记忆、Skill、Prompt、工具模板、评测集、专家规则、可执行 ADR | 有 owner、有版本、有评测门槛、有废弃策略 |

**可执行 ADR（Architecture Decision Records）** 值得单独强调：从散文式决策记录，升级为带范围、约束语言（ALWAYS / NEVER）、关联 fitness test 的机器可读治理资产，供 Agent 在改动前查询、在 CI 中强制。[^arch-as-code]

随使用加深，底层资产增加，本体完善，记忆与 Skill 进化。新资产不是堆更多文件，而是让知识、经验与执行轨迹成为人与智能体都能理解、检索、调用与进化的组织资产。

## 9. 新工具：智能中枢与 Harness 工程

谈新工具，不宜从「多了哪些 AI 工具」起笔，而应从企业软件体系如何扩展、以及 **Agent 如何被可靠地放进生产** 看起。

### 9.1 既有系统类别（业界术语）

Geoffrey Moore 提出 **Systems of Record**（记录系统）与 **Systems of Engagement**（互动系统）的区分；业界后续又常用 **Systems of Insight**（洞察系统）描述分析与预测能力。[^moore-2011][^govexec-soi] 在软件工程语境下，可再显式拆出交付系统：

| 系统 | 职责 | AI 时代要点 |
| ------ | ------ | ------ |
| **System of Record** | 记录确定性事实（客户、订单、库存、审计等） | 更重要：智能体行动需要可靠事实底座 |
| **System of Engagement** | 人机互动入口（门户、协同、审批、触点） | 仍是人进入系统的主入口 |
| **System of Insight** | 报表、分析、指标、实验 | 回答看见什么、理解什么、预测什么 |
| **System of Delivery** | 需求、代码、CI/CD、测试、环境、发布、缺陷、复盘 | 从服务人类 → 同时服务人类与智能体 |

Delivery 真正在变：除工作项外，还要管 Agent 身份/权限/任务队列、执行日志、工具调用、上下文引用、Skill 版本、评测、Token 成本、质量门禁与人工审核。其上长出 **人智协同平台（Delivery Workbench）**——仍属 Delivery 的 AI 化扩展，连接人、任务、代码与智能体，并衔接下文的智能系统。

### 9.2 新增两层（本文扩展）

**System of Ontology（本体）**：不是普通知识库，而是把业务概念、系统边界、实体、契约、规则、测试、指标、决策与缺陷连起来；既接 Record 的事实，也接 Delivery 的工程资产与 Insight 的指标。没有它，智能体只能做相似度检索，易找错上下文、误解概念、遗漏约束。Palantir 等实践中，「客户侧本体」正是 FDE 工作的核心产出之一。[^palantir-fde]

**System of Intelligence（智能）**：与 Insight 区分——Insight 回答「看见/理解/预测」；Intelligence 回答「怎么做、谁做、用什么工具、如何验证、何时人审」。它是新中枢：大模型、Agent 运行、多智能体、工具、记忆、规划、评测、权限、风险分级与 Human in the Loop。

智能体可粗分两类：

| 类型 | 定位 | 价值 |
| ------ | ------ | ------ |
| **桌面智能体** | 个人助手，跟随个人上下文 | 增强个人工作半径 |
| **云端智能体** | 企业数字员工（身份、权限、队列、日志、责任） | 增强组织执行力；须受审计、成本、质量门禁约束 |

### 9.3 Harness Engineering：把模型变成可生产系统

模型能力是租来的；决定能否稳定进生产的，往往是周围的 **Harness（挽具 / 运行时脚手架）**。业界常把生产级 Harness 拆为五层：[^harness]

| 层 | 作用 | 典型能力 |
| ------ | ------ | ------ |
| **工具编排** | 控制 Agent 如何调用 shell / API / IDE / MCP | 工具白名单、会话、插件、技能路由 |
| **验证环** | 中间结果可自动判定对错 | 单测、契约、自检、评测器、金丝雀 |
| **上下文与记忆** | 提供正确上下文并沉淀经验 | 仓库指令、本体检索、记忆、轨迹 |
| **护栏** | 硬边界 | 沙箱、权限分级、预算上限、HITL 门禁 |
| **可观测性** | 可调试、可审计、可度量 | 轨迹日志、成本归因、成功率、回归板 |

> **核心变化**：不是把 AI 接到旧系统上，而是以 System of Intelligence 为中枢，把 Delivery 升级为人智协同工作台，并由平台提供可复利的 Harness——不是一个 AI IDE 或几个插件，而是一整套生产基础设施。

## 10. 新治理：安全网、风险分级与度量

AI 越强，越不能靠「层层审批、人工兜底」。它提速，也带来不确定性：误解上下文、看似合理实则有缺陷、局部优化破坏边界、错误方向持续推进。把每一步都拉回人工审批，会把速度优势抵消掉。

更合理的顺序：

> **先建可验证安全网，再逐步放大 Agent 自主度。**

这与 DORA 观察一致：AI 可提升吞吐，但若控制系统（测试、版本控制、快速反馈、松耦合）不足，变更量上升会转化为不稳定性。[^dora-2025] 也与 NIST AI RMF 的精神一致：先 **Govern / Map**，再 **Measure / Manage**，把人类—AI 配置与问责写清楚。[^nist-ai-rmf]

### 10.1 第一步：多层自动化测试

治理的起点。AI 改代码后，最重要的反馈不是「看起来对不对」，而是系统能否自动验证有没有破坏功能、接口、数据、权限与性能。单元、接口、契约、E2E、回归、性能基线、安全扫描、Agent Eval、造数脚本，都应成为反馈机制。安全网越强，自主范围越大；没有测试与环境，就算写代码很快，组织也不敢合并、重构与发布。

先问「AI 做完后能不能快速验证」，再问「要不要让 AI 自主」。

**Agent Eval** 建议与产品测试分开管理：既评最终代码正确性，也评轨迹质量（工具误用、幻觉引用、越权尝试、成本异常）。评测集应版本化，并随失败案例持续扩充。

### 10.2 第二步：AI 参与评审

安全网具备后，让 AI 更早参与需求、设计、架构、代码、测试缺口与文档一致性评审。价值是前置发现与并行辅助，不是替代责任人，也不是制造新排队。这正是缓解 Faros「评审瓶颈」的关键路径：用机器可读规则与 AI 辅助，降低人类评审负荷，而不是让人去读更多、更大的 PR。[^faros-2025]

DORA 还指出约 **30%** 受访者对 AI 生成代码信任很低——评审与验证技能因此成为必备能力，而非可选项。[^dora-2025]

### 10.3 第三步：规则守护与熵减

治理不能只靠人看文档或一次性评审。分层依赖、领域边界、契约兼容、关键模块测试、敏感数据访问、公共能力不重复实现——应变为可持续执行的脚本、检查与流水线门禁。

这与 **Architecture as Code / 架构适健函数（fitness functions）** 一脉相承：把架构意图变成可版本化、可测试、可进入 CI 的约束；AI 可解释与辅助，但不应替代高风险决策的人类责任。[^arch-as-code][^evo-arch]

AI 也可帮技术债：扫描重复代码、过期依赖、低覆盖、复杂度异常、接口不一致、文档缺失、架构偏离；更重要的是拆成低风险、可验证、可回滚的小任务，在自动化测试保护下日常推进——熵减成为日常，而非一年一次大工程。

### 10.4 第四步：风险分级与 Human in the Loop

| 风险 | 治理强度 | 示例 |
| ------ | ------ | ------ |
| **低** | Agent 在自动化测试与质量门禁下可自主完成 | 文档、测试补强、局部重构且测试绿 |
| **中** | 人工确认方案或关键结果 | 跨服务改动、中等范围 API 变更 |
| **高** | 关键节点必须人把关 | 资金、权限、隐私、安全、核心交易、关键架构、大范围迁移 |

Human in the Loop 不是每步批准，而是在真正重要的决策点保留人类责任。NIST AI RMF 要求明确区分不同 human–AI 配置下的角色与职责，并留下可审计证据。[^nist-ai-rmf] 风险分级既决定自主度，也决定责任归属。

### 10.5 第五步：效能度量与 AI FinOps

不能只看「用了多少 AI」，还要看「带来了什么收益」。建议至少同时看三类指标：

| 类别 | 指标示例 | 用途 |
| ------ | ------ | ------ |
| **交付系统（DORA 等）** | 部署频率、变更前置时间、变更失败率、恢复时间 | 看组织级吞吐与稳定性是否同向改善 |
| **AI 协作** | Agent 辅助 PR 占比、评审等待、PR 体积、返工率、评测通过率 | 看加速是否转化为可合并、可维护的变更 |
| **成本与价值（FinOps）** | Token/调用成本、单 PR 成本、成功率、上线业务指标 | 看投入产出与浪费 |

FinOps（云成本运营）在 AI 时代自然延伸到 **Token / Agent 运行成本**：可见、可归因、可优化，并与交付价值对照。[^finops]

AI 会放大人员能力差异——有人只补文案，有人能澄清需求、出原型、构造测试、重构并沉淀 Skill。度量真实影响，才能推动培训、最佳实践与 Skill 复用。

治理目标不是让 AI 慢下来，而是让它在可控边界内跑得更快：速度、质量、责任与价值同时可控。

## 11. 常见反模式

在推广 5+2 之前，先避开这些高频陷阱：

| 反模式 | 表现 | 为何有害 | 纠正方向 |
| ------ | ------ | ------ | ------ |
| **工具撒网** | 全员发许可证，无流程无基线 | 局部加速、全局无感；无法复盘[^faros-2025] | 先试点、先度量、先安全网 |
| **只加速非约束** | AI 狂写代码，评审/环境不动 | Amdahl：收益被最慢环节吃掉 | 用价值流找出真实约束再投放 AI |
| **审批墙换皮** | 把人工评审原样搬到 Agent 每步 | 吞吐优势被抵消 | 风险分级 + 自动化门禁 |
| **Prompt 部落知识** | 高手口口相传，无 Skill/评测 | 能力不可复利、不可治理 | Skill 化、版本化、评测门槛 |
| **无 Harness 的自治** | 直接给 Agent 生产权限 | 事故与越权成本高 | 沙箱、权限、预算、HITL[^harness] |
| **大图谱先行** | 先做企业级本体再交付 | 周期长、难验证、易空转 | 围绕试点产品长出本体雏形 |
| **组织运动式改名** | 先改岗位名与汇报线 | 缺工程底座，形式大于内容 | 产品试点证明后再扩展编制 |
| **指标虚荣** | 只报生成代码行数/对话次数 | 与稳定性、价值脱钩 | DORA + 质量 + 成本 + 业务结果 |

## 12. How：先让一个产品跑起来

把前面全部摊开，容易得出「组织要全面转型」——方向没错，但不能一上来改组织、改岗位、改考核，那样风险高，也易变成运动。DORA 亦建议把 AI 采纳当作**组织转型**：先澄清政策、连接内部上下文、强化基础实践与安全网、投资内部平台、对准终端用户。[^dora-2025]

更好的切入：选合适产品，从工程底座做起，先跑通「人与智能体可稳定协同」，再复制。

| 阶段 | 窗口 | 目标与关键动作 | 建议退出标准（示例） |
| ------ | ------ | ------ | ------ |
| **0** | 启动前 2–4 周 | 选试点：真实业务、有代码/测试基础、愿意尝试、权责清晰。建基线（DORA 四项、缺陷、返工、覆盖、评审周期、环境准备、澄清次数、业务指标）。划定 Agent 可改范围与禁区；发布最小 AI 使用政策 | 基线可复现；禁区书面化；成功标准书面化 |
| **1** | M1–M2 | 工程底座：CLI、环境自动化、测试补强、造数、质量门禁、资产 Git 化、基础适健函数。看起来不够「AI」，却是后续闭环前提 | 主干变更可自动验证；关键路径有回归 |
| **2** | M2–M4 | 产品 AI 小队：产品 + Application Builder + Agent/Skill Builder。跑通快速原型、契约驱动交付；引入最小 Harness（验证环 + 轨迹日志） | 小队吞吐↑且缺陷率不恶化；至少 3 个可复用 Skill |
| **3** | M3–M6 | 数据与知识：平台前置 FDE；沉淀口径/脚本/指标；围绕试点产品建本体雏形；评测集版本化 | Agent 能稳定取到正确上下文；幻觉引用显著下降 |
| **4** | M6–M9 | 融合型 FDE：应用+数据+知识前置业务；人智协同平台接入；企业智能体承担可重复、可验证、风险可控任务；FinOps 看板 | 中低风险任务可在门禁下半自动合入；成本可归因 |
| **5** | M9–M18 | 组织转型：FDE 领域团队、产品线小队、平台底座；治理与 ROI 制度化；按 Team Topologies 澄清互动模式 | 多产品复用同一平台能力；公司层吞吐与稳定性同向改善 |

> **关键判断**：不是先把组织图画漂亮，而是先让一个产品具备 AI 可协同的工程底座；再用试点成果复制到更多产品与领域。每一阶段沉淀 5+2 的一部分——角色在试点中长出，组织在协同中演化，工艺与流程在真实交付中跑顺，资产随使用沉淀，工具围绕真实任务建设，治理基于真实风险与数据闭环。

只有这样，AI 才不会停在个人工具，而会逐步变成组织能力。

---

## 13. 结语

AI 时代软件工程的变革，不是「要不要用 AI」——答案已经很明显。

真正的问题是：个人提效之后，组织如何承接？

5+2 不是完美蓝图，而是更务实的提问与操作系统：当每个人都变快了，组织能不能建立一套新的生产关系，让这些效率真正变成系统性竞争力——并且在加速时守住稳定性、责任与成本？

实证与理论反复指向同一方向：

- 工具普及不等于组织绩效；[^faros-2025]
- AI 是放大器，底座差则放大混乱；[^dora-2025]
- 瓶颈会转移到澄清、评审、测试、发布与跨团队协调；
- 可租用的是模型，应自建并复利的是 **Harness、资产、平台与治理**。[^harness]

谁先把验证、资产、流程与治理补齐，谁才更可能把个人速度变成组织速度。

如果你也在想「AI 强了，组织怎么还没变快」，希望这篇文章能带来一点可操作的启发。
